```markdown
## 为什么做这个项目

我平时会和外国笔友聊天、写邮件，但自己的英语不太好。

直接让 AI 生成整封邮件虽然方便，内容却可能偏离我原本想表达的意思。相比让 AI 替我写，我更希望它像代码补全一样，在需要的时候提供下一步建议。

于是我产生了一个想法：

既然写代码可以自动补全，写英语为什么不行？

## 当前实现的功能

- 根据上下文补全单词、短语和句子
- 按 Tab 接受补全，按 Esc 忽略
- 检查语法和不自然的英文表达
- 在原文中标出问题
- 使用中文等语言解释修改原因
- 一键应用修改
- 润色、简化和解释表达
- 本地保存草稿
- 打开及保存 TXT、Markdown 文件

## 项目结构

项目主要由三部分组成：

HTML / CSS / JavaScript 前端
            |
            v
      Python 本地服务
            |
            v
    用户选择的 AI 模型 API

前端负责编辑器、补全展示、检查结果和写作交互。

Python 服务负责模型请求、本地配置、文件操作，以及桌面应用需要的系统能力。

Windows 桌面版使用 WebView2 显示界面。应用启动时会自动寻找空闲的本地端口，再打开本地写作页面。发布版本会把运行环境一起打包，普通用户不需要另外安装 Python。

## 为什么第一版采用 BYOK

第一版没有提供共享 AI 额度，需要用户配置自己的模型服务地址、API Key、模型 ID 和接口类型。

这样可以让用户自由选择兼容的模型服务，也避免把开发者自己的密钥放进客户端。

Windows 桌面版使用 DPAPI 加密 API Key，配置保存在当前 Windows 用户的本地应用数据中。草稿默认也保存在本地。

BYOK 同时提高了使用门槛，因此当前版本主要适合熟悉模型 API 的程序员和 AI 工具用户。

## 开发过程中遇到的问题

### 补全不能只看最后一句

如果只把光标附近的文字发送给模型，补全内容很容易和前面的草稿冲突。补全需要结合文体、读者、语气和草稿上下文，同时控制返回长度。

### 检查结果必须能够定位原文

为了让用户直接应用修改，检查结果需要包含原文片段、替换建议、原因和位置。前端再根据这些信息标出问题并替换对应内容。

### AI 功能不能阻塞写作

补全和检查可能受到网络速度、模型响应速度及限流影响。界面必须允许用户继续输入、忽略建议或重新检查。

### 桌面应用不只是套一层网页

做成 Windows 应用以后，还需要处理本地端口、后台服务清理、文件读写、API Key 保护、安装包、便携版、隐私政策、商店素材和审核材料。

真正花时间的不只是调用模型，而是把完整的使用流程做出来。

## 当前不足和计划

第一版需要自备模型 API，没有账号和跨设备同步，也没有完整的学习记录。

后续会继续降低配置门槛，面向普通英语学习者，并考虑加入常见问题统计、修改前后对照、表达收藏和针对性练习。

做完第一版以后，我最大的感受是：调用模型只是 AI 应用里很小的一部分。

一个真正能交给用户使用的应用，还需要处理交互、错误状态、隐私、本地存储、打包、测试、文档和发布。

项目采用 MIT 开源协议，欢迎体验和交流：

https://github.com/ETOLucy/WriteMelo

请不要在公开评论或 Issue 中粘贴 API Key，也不要上传包含隐私的真实邮件内容。
```

```markdown
因为我的英语不太好。

每次和外国笔友聊天、写邮件，我通常不是完全不知道该说什么，而是知道自己想表达什么，却不知道怎样用英语自然地写出来。

我试过直接让 AI 生成邮件。它确实能给出一封语法正确、表达流畅的成品，但还有一个问题：那封邮件越来越像 AI 想说的话，而不是我想说的话。

后来我想到，写代码时的自动补全似乎提供了另一种思路。

代码补全不会一开始就替你写完整个项目。你先确定方向、写下一部分内容，它再结合上下文提供下一步建议。你可以接受，也可以忽略。

那么，写英语能不能也这样？

于是我做了 WriteMelo，一个像代码补全一样的英文写作工具。

## 它不是替你写，而是陪你把原来的意思写出来

使用时，用户仍然需要自己开始表达。

WriteMelo 会结合前面的草稿，补全接下来的单词、短语或句子。按下 Tab 接受，按下 Esc 忽略。

写完以后，它还会检查不自然的表达，在原文中标出问题，并用中文等用户熟悉的语言解释修改原因。

我认为“解释原因”很重要。

很多工具可以把错误句子改成正确句子，但如果用户不知道为什么要这样改，下次很可能仍然会犯同样的问题。

所以我希望它不仅给答案，也能帮助用户逐渐理解英语表达。

## 为什么第一版更适合程序员

由于主包比较懒，第一版走的是朴素实用路线。

目前软件不会赠送 AI 额度，需要用户自行配置兼容的模型 API、API Key 和模型 ID。这对熟悉 API 的程序员并不复杂，对普通英语学习者却仍然是一个明显门槛。

因此，第一版更适合同时有英文写作需求、又熟悉 AI 模型服务的程序员朋友。

用户可以自行选择模型服务。草稿默认保存在本地，Windows 桌面版会使用系统加密能力保护本地 API Key。

需要说明的是，软件本身可以免费下载，但调用 AI 模型可能产生费用，具体由用户选择的服务商决定。

## 第一版能做什么

- 上下文英文补全
- 单词、短语和句子模式
- 英文表达检查
- 中文等语言的修改解释
- 一键修改、润色和简化
- 书信、作文和消息格式
- 本地草稿
- TXT 和 Markdown 文件读写

它还不支持云同步，也没有内置模型额度和完整的个人学习记录。

## 后续计划

接下来会继续降低使用门槛，希望最终能让普通英语学习者也能开箱即用。

同时计划增加真正与学习有关的功能，例如记录用户经常出现的问题、保存修改前后的对照、收藏有用表达，并根据真实错误生成练习。

这些目前都还是后续计划，不是第一版已经提供的功能。

Windows 应用商店版本已经提交，目前正在审核，等待正式上架。现阶段可以从 GitHub 下载 Windows 安装版或便携版。
```

# 九、SegmentFault 思否

## 发布定位

思否适合技术设计文章。建议围绕“如何设计一个本地优先的 BYOK AI 桌面应用”，WriteMelo 作为案例出现。

## 标题

```text
从模型调用到 Windows 应用：一个 BYOK AI 写作工具的工程化实践
```

## 正文

```markdown
调用一次大模型接口并不困难，但把它做成一个能够交给用户安装和使用的桌面应用，需要处理的事情远不止请求 API。

最近我完成了一个开源项目 WriteMelo。它是一款采用代码补全式交互的英文写作工具，支持上下文补全、英文检查、母语解释和一键修改。

项目地址：

https://github.com/ETOLucy/WriteMelo

本文主要复盘三个工程问题：

1. 如何划分前端、本地服务与模型服务的边界；
2. 如何处理 BYOK 配置和本地密钥保护；
3. 如何把网页交互打包成可安装的 Windows 应用。

## 一、为什么采用本地服务

WriteMelo 的写作界面使用 HTML、CSS 和 JavaScript 实现，本地 Python 服务负责模型请求、配置和文件操作。

结构如下：

前端写作界面
     |
     v
Python 本地服务
     |
     v
用户选择的模型服务

这种结构让前端不需要直接持有 API Key，也方便桌面版统一处理文件读写、模型请求和系统能力。

桌面应用启动后会寻找空闲的本地端口，再在 WebView2 中打开写作界面。应用退出时，本地服务也需要一起清理。

## 二、BYOK 不只是增加一个设置页面

第一版要求用户配置模型服务地址、API Key、模型 ID 和接口类型。

这意味着应用必须处理：

- 地址和模型 ID 校验
- Chat Completions 与 Responses 两类接口
- 身份验证失败
- 模型不存在
- 网络超时和限流
- 保存前的连接测试
- 配置更新后的即时生效

Windows 桌面版使用 DPAPI 加密本地 API Key。这样可以把密钥与当前 Windows 用户绑定，而不是把明文 Key 写进前端代码或安装包。

不过 DPAPI 只解决本地静态存储问题。使用 AI 功能时，相关文本仍然需要发送给用户选择的模型服务商，因此产品必须明确披露数据流向。

## 三、补全与普通对话请求不同

英文补全需要返回短、稳定、能够直接插入光标位置的内容。

如果提示词只强调“继续写”，模型很容易生成过长内容；如果上下文不足，补全又会偏离文章意图。

因此请求需要同时携带：

- 当前文体
- 目标读者
- 用户英语水平
- 语气
- 光标前的草稿上下文
- 用户选择的补全粒度

前端还需要处理过期请求。用户继续输入后，之前返回的补全可能已经不再适用，不能无条件插入编辑器。

## 四、检查结果需要结构化

检查功能不能只返回一段自然语言说明。

为了在原文中标记并一键修改，每个问题至少需要包含：

- 原文片段
- 替换建议
- 修改原因
- 问题类别
- 原文位置

前端根据位置渲染标记，同时要考虑用户在检查过程中继续编辑，导致原始位置失效的情况。

## 五、从网页到 Windows 应用

完成网页功能以后，桌面发布还需要处理：

- WebView2 运行环境
- 本地服务端口
- 文件打开和原子保存
- 外部文件变化与覆盖提示
- 安装版和便携版
- 图标与版本信息
- 隐私政策和支持页面
- Microsoft Store 身份及 MSIX 包

这些工作不属于模型能力，却直接决定用户是否能够稳定使用产品。

## 六、当前边界

WriteMelo 第一版不提供内置模型额度、云端账号或跨设备同步。

草稿默认保存在本地，用户自行选择模型服务。软件可以免费下载，但模型调用费用由对应服务商收取。

Microsoft Store 版本已经提交，目前正在审核，等待上架。

## 总结

AI 应用的工程化重点不是“能不能调用模型”，而是如何让模型能力在真实交互、错误状态、隐私边界和桌面环境中稳定工作。

WriteMelo 采用 MIT 协议开源，欢迎查看实现和提出建议：

https://github.com/ETOLucy/WriteMelo
```

# 十一、CSDN

## 发布定位

CSDN 更适合可被搜索的技术教程。推荐写“如何保护桌面 AI 应用中的 API Key”，项目作为完整案例。

## 标题

```text
从网页到 Windows：使用 Python、WebView2 和 DPAPI 构建 BYOK AI 桌面应用
```

## 正文

```markdown
很多 AI Demo 会直接在前端代码中调用模型接口，但一旦准备发布桌面应用，就必须重新考虑 API Key、本地服务、文件能力和安装包边界。

本文以开源英文写作工具 WriteMelo 为例，介绍一个 BYOK Windows AI 应用的基本结构。

项目地址：

https://github.com/ETOLucy/WriteMelo

## 一、整体结构

WriteMelo 的界面由 HTML、CSS 和 JavaScript 实现，本地 Python 服务负责模型请求、配置和系统能力。

前端写作界面
     |
     v
Python 本地 HTTP 服务
     |
     v
用户选择的模型 API

桌面程序启动时：

1. 寻找一个空闲的本地端口；
2. 启动 Python 本地服务；
3. 等待服务就绪；
4. 在 WebView2 窗口中打开本地地址；
5. 退出窗口时清理本地服务。

## 二、为什么不应该把 API Key 写进前端

只要密钥进入前端 JavaScript、安装包资源或公开仓库，就不能再被视为秘密。

第一版采用 BYOK，每个用户配置自己的模型服务地址、API Key 和模型 ID。

前端只与本地 Python 服务通信，由本地服务完成实际的模型请求。

## 三、使用 DPAPI 保护本地 API Key

在 Windows 桌面版中，可以使用 DPAPI 把加密数据与当前 Windows 用户绑定。

基本流程是：

1. 用户在设置页面输入 API Key；
2. 本地服务测试模型连接；
3. 测试成功后使用 DPAPI 加密；
4. 将加密结果写入当前用户的应用数据目录；
5. 发起模型请求时在内存中解密使用。

DPAPI 主要降低本地配置文件被直接读取后泄露明文 Key 的风险，但不能替代系统账号安全，也不能改变模型请求需要发送到服务商这一事实。

## 四、补全请求的工程问题

补全与普通聊天不同，它需要：

- 返回内容足够短
- 能直接插入当前光标
- 避免重复用户已经写过的内容
- 与整篇草稿意图一致
- 用户继续输入后丢弃过期结果

因此，除了提示词，还需要在前端维护请求状态和草稿版本，避免旧补全覆盖新输入。

## 五、桌面文件能力

Windows 版支持打开和保存 UTF-8 编码的 TXT、MD、Markdown 文件。

保存时需要考虑：

- 文件编码
- 文件大小限制
- 外部程序已经修改文件
- 覆盖前提示
- 原子保存
- 另存为独立副本

这些能力通过本地服务和桌面桥接完成，而不是让网页获得任意文件访问权限。

## 六、打包和发布

发布版本需要把 Python 运行环境、应用资源和桌面启动逻辑一起打包。

项目同时生成：

## 七、项目边界

WriteMelo 第一版：

- 不提供共享 AI 额度
- 不包含维护者的模型 Key
- 不提供云账号和跨设备同步

https://github.com/ETOLucy/WriteMelo
```
